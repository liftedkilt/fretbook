# How Fretbook is built

```
browser   Svelte 5 + TypeScript (Vite)    alphaTab renders and plays tabs; pdf-lib writes the PDF; ChordSheet.svelte renders chord sheets
server    FastAPI (fretbook/)             one process, background job thread for imports
storage   SQLite data/fretbook.sqlite     songs, users, sessions, jobs; audio files under data/media/<owner>/<song>/
auth      fretbook/auth/                  single-user, or OIDC code flow + PKCE with roles from groups
```

FastAPI serves the built web app, so the container needs no Node at runtime. `<base href>` is rewritten from `FRETBOOK_ROOT_PATH`.

PDF export adds two web dependencies, [`pdf-lib`](https://pdf-lib.js.org/) and [`@pdf-lib/fontkit`](https://github.com/Hopding/fontkit) (`web/package.json`). Vite bundles them with the app. The music font is Bravura from `@coderline/alphatab`, copied into `font/` by the Vite plugin. fontkit reads its glyph outlines and the PDF draws those as vectors, so the font file itself is not embedded. The Docker image does not install anything extra for PDF.

## Stored formats

A song is either a **tab** or a **chord sheet**.

- **Tabs** are stored as a Fretbook JSON score document (`fretbook/score/model.py`). It is not alphaTex and not tied to alphaTab: the browser turns it into alphaTex only to render. MusicXML would be the other candidate, but it is far harder to validate, edit in place, and attach sync data to, and every import would round-trip through it. Portability comes from the MusicXML export instead, which the importer reads back (tested), so a library is never locked in.
- **Chord sheets** are stored as ChordPro text and rendered by a small component of our own. alphaTab is built around bars of notation, which suits tabs but makes a chord chart look stiff.

## The score document

- `bars` are song-level (time signature, tempo changes, repeats, section names), like alphaTab's master bars. Each track has exactly one entry per bar with only its notes, in one or more voices.
- Time is integer ticks, 960 per quarter note (alphaTab's resolution), so triplets and other tuplets are exact.
- String index 0 is the highest string, as in Songsterr and MusicXML `<string>`. `tuning_midi` lists the strings highest first. alphaTab numbers strings from the lowest; `web/src/lib/alphatex.ts` and `web/src/lib/alphatab/importScore.ts` convert.
- Techniques (hammer-on/pull-off, slides, bends, vibrato, harmonics, ghost/dead notes, palm mute, let ring, staccato, grace notes) are typed fields.
- `sync.points` (published per-bar times) and `sync.anchors` (your taps) are keyed by bar index. Bar timing between marks is piecewise linear and follows each bar's real length (`fretbook/score/sync.py` and `web/src/lib/sync.ts` implement the same algorithm and share test vectors). Repeats are stored but not rendered yet, so the bar index is also the playback order.

## API conventions

- The contract is the committed `openapi.json`, and `web/src/lib/api-types.ts` is generated from it. See [CONTRIBUTING.md](../CONTRIBUTING.md#api-contract).
- Every write bumps a song's `revision`. `PUT /api/songs/{id}` must send the revision it loaded and gets `409` if the song changed.
- `GET /api/songs` is paged and searched on the server: `q` (word prefixes over title, artist, the lyrics of chord sheets and tags, matched with the `songs_fts` FTS5 table; triggers keep title, artist and tags in step, and the repository writes the lyrics, chord markers and directives stripped by `chordpro.lyrics`, whenever a song's content is saved, with `refresh_lyrics` filling in older sheets at start-up; all columns weigh the same and the sort keys decide the order), `sort` (`title`, `artist`, `added`, `updated`, `opened`), `order`, `instrument`, `limit` (1 to 200) and an opaque `cursor`. It returns `{items, total, next_cursor, counts}`, where `counts` covers the whole library for the filter chips. An item that the search found through its lyrics, and not its title, artist or tags, carries `lyrics_snippet`: FTS5 `snippet()` of the lyrics, matched words between U+0002 and U+0003, which the library card shows (`web/src/lib/lyricsSnippet.ts`). The cursor is an offset, so a song added between two page requests can shift the next page by one. `POST /api/songs/{id}/opened` records `last_opened_at` without touching `revision` or `updated_at`.
- Tags and the favourite star are per song and so per user (`song_tags`, with a case-folded `tag_key`, and `songs.favourite`). `GET /api/songs` takes repeated `tag` parameters (a song needs all of them) and `favourite=true`; `counts` ignores both, and adds `favourites`. `PUT /api/songs/{id}/tags`, `PUT /api/songs/{id}/favourite`, `POST /api/tags/add` and `GET /api/tags` change and list them, and `PATCH /api/tags/{tag}` (rename, or merge when the new name exists; a song that ends up with both keeps one) and `DELETE /api/tags/{tag}` change a tag on every song of the caller (the library's "Manage tags" sheet). Like `opened`, they never touch `revision` or `updated_at`. `fretbook/tags.py` holds the tag rules and `suggest_tags`, which imports apply to a new song. The library archive lists each song's `tags` and `favourite` in its manifest entry.
- Errors are `{"detail": {"key", "message", "params"}}`. The web app shows `errors.<key>` from its catalog and falls back to the English message, so server errors can be translated. Job progress uses keys too.
- Schema changes are numbered SQL files in `fretbook/db/migrations/`, each applied in one transaction. Before applying pending migrations on start, a consistent SQLite snapshot is backed up to `data/backups/pre-migrate-<from>-<to>-<timestamp>.sqlite` (keeping the last N). The server refuses to start if the database schema is newer than the code.
- Backups: `fretbook/backup/` writes and restores the library zip (`manifest.json` plus `songs/<id>/…`; restore is the `library.import` job and never extracts by archive name), and `python -m fretbook backup` takes the cron snapshot (`snapshot.py`).

## Transpose and retune

`fretbook/score/retune.py` (`convert_track`) returns a new `Track` and a report for one track; it never edits the source. Options: `semitones`, a new `tuning` and `capo`, `keep` (`pitch`: the music sounds the same, `shape`: the frets stay and the tuning or capo changes, same string count only) and `reduce` (`lowest` keeps the lowest note of each beat; `root` keeps the root of the chord the beat sounds: `chord_root_note` tries each sounding pitch class as a root against a small table of triads, suspensions, sevenths and sixths, extensions allowed on top, the shape with the most tones wins, a tie goes to the lowest note, and a beat with no recognised chord or without its root falls back to the lowest note). In `pitch` mode every beat is tried on the same strings first (the string's open pitch must have moved by at most five semitones, so a guitar part on a bass is refingered instead of sent up the neck; the new fret must be 0 to 24 and a chord must still fit a four-fret stretch); the beats that do not fit go through `fingering.assign_frets` together, which moves unreachable pitches by octaves and thins chords nothing can hold. Both are reported by bar, not silently. A tie copies the placement of the note it continues, found by its old string and fret in the closest earlier beat, so a chain of ties follows a re-fingered note. Dead notes keep their string (clamped), and a natural harmonic that moved is turned into a plain note and counted. Voices are converted independently, and bars, rests and everything else are copied.

`fretbook/api/retune_routes.py` is `POST /api/songs/{id}/convert`: `mode=preview` saves nothing, `add` inserts the result after the source with a new id (`<id>-2`, ...) and not preferred, `replace` keeps the track's id. Saving uses `update_song` with the client's `revision`, so a stale one is a 409. `RetuneSheet.svelte` (opened from `TabPlayer.svelte`) previews with a debounced call and draws the result with `TabPreview`; its logic is in `web/src/lib/retune.ts`. Capo suggestions for chord sheets are client-side only (`web/src/lib/capo.ts`, `CapoSuggestions.svelte`): each capo from 1 to 7 lowers the sounding chords and is kept when it leaves fewer barre chords than the current capo.

## ASCII tab

`fretbook/importers/midi.py` reads a Standard MIDI File (via `mido`) into one *source* per track and channel (channel 10 is skipped), converts ticks to 960 per quarter, snaps notes to a grid (a quarter of a bar whose onsets fit a triplet, quintuplet or sextuplet better than the grid becomes `Beat.tuplet` beats; a note that rings two or more grid units past the next onset moves to a second voice instead of being cut), builds bars from the time-signature events (a signature takes effect at the next bar line, a tempo change on the bar after it), ties notes across bar lines, and splits long notes and rests into drawable values with `ascii_tab._fill`. Which string and fret each pitch gets is not the importer's business: `fretbook/score/fingering.py` (`assign_frets`) does a Viterbi pass over per-group candidates (distinct strings, a four-fret stretch for chords) minimising the movement of the hand (a note still ringing at the next group is passed again with `holds`, so both MIDI voices are fingered together and it stays on its string), with a mild preference for low frets, and reports groups it had to octave-shift or thin out. It has no format dependencies so transcription and retune can reuse it. `fretbook/api/midi_routes.py` has the stateless `inspect` endpoint, the import endpoint (queues `import.file` with `kind=midi` and the choices in `payload.midi`, which `_options` hands to the importer) and `export.mid`, written by `fretbook/export/midi.py` in played order. `MidiImport.svelte` is the dialog, opened by `AddSheet` when the dropped file starts with `MThd`.

`fretbook/importers/ascii_tab.py` turns `e|---3---|` text into a score document. Rhythm is estimated, not read: a bar's notes are placed by their position between the bar lines, snapped to a grid (eighth notes by default), and each note lasts until the next one, rounded down to a length the notation can draw, with rests for the rest of the gap. The song is stored with `source_ref.rhythm_estimated = true`, which the song page shows as a badge. `looks_like_ascii_tab` is the one test that tells a tab from a chords-over-lyrics sheet; the importer registry uses it for `.txt` files and `POST /api/imports/ascii-tab[/preview]` for pasted text.

## Exercise generator

`web/src/lib/exercises/` builds practice exercises in the browser; the server only stores the result through `POST /api/songs/import-document` (source kind `manual`, tag `exercise`), so no API changes were needed. `theory.ts` holds the scale tables (each with the parent major key whose CAGED shape it sits in) and the CAGED window offsets. `generate.ts` has one generator per kind. Scales and arpeggios take every pitch of the pitch-class set inside a five-fret position window (one spot per pitch, nearest the window's middle), then cut it to the tonic and range. Spider drills walk fret by finger number across the strings. Chord changes take the best voicing from `chords/voicings.ts` and strum it from a one-token-per-eighth pattern (`D`, `U`, `-`), and bass patterns derive pitches from the chord and place them with a small Viterbi pass that keeps the hand close. `layout` fills 4/4 bars and splits and ties anything that crosses a bar line. Generators throw `ExerciseError` with a catalog key, which `ExercisesView.svelte` shows. `presets.ts` lists the preset drills.

## Universal import

`POST /api/imports/auto` (`fretbook/api/universal_routes.py`) takes one of a file, pasted text or a link and queues a job; the old per-format endpoints stay. `fretbook/importers/sniff.py` identifies formats by content (magic bytes, ZIP member names, then text heuristics; the extension is only a fallback), and `resolve_importer` uses it for every uploaded file, so a mislabelled file still reaches the right importer. Prose that matches no format is refused rather than turned into a chord sheet. Guitar Pro is parsed by alphaTab, in the browser (the web app checks for it first, `web/src/lib/sniff.ts`) and on the server: `fretbook/importers/guitarpro.py` runs `web/scripts/gp-to-document.ts`, bundled with alphaTab into one `gp-to-document.mjs` (`npm run build:gp-cli`), under Node. Browser and server share `web/src/lib/alphatab/convert.ts`, so a file becomes the same document either way (`tests/test_guitarpro.py` compares them against `tests/fixtures/corpus/golden-web`). The alternative, PyGuitarPro for GP3-5 plus a hand-written GP6/GP7/GP8 reader, would be a second parser that could disagree with the browser and would need its own GPX (BCFZ) and GPIF code; it was rejected for that reason. The cost is Node in the image (about 120 MB unpacked, 43 MB compressed, plus a 2.4 MB script).

Links go through the provider registry in `fretbook/importers/remote.py`: Songsterr, YouTube (blank tab plus `AudioFetch`), Ultimate Guitar (`ultimate_guitar.py` reads the page's `js-store` JSON; chords go through `from_chords_over_lyrics` and tabs through `ascii_tab.parse`; `source_ref.tab_id` lets `_store_result` refresh an untouched import in place, like Songsterr's `song_id`), and everything else, which `SafeFetcher` (`safe_fetch.py`) downloads and the sniffer classifies; an HTML page is searched by `pages.py` for linked score files, then `<pre>` tab blocks. `SafeFetcher` is the only way the server fetches a user-supplied URL: public addresses only (unless `FRETBOOK_ALLOW_PRIVATE_URLS`), connect to the checked address with the original `Host` and SNI, manual redirects re-checked per hop, size and deadline limits. A new site is a new `Provider` plus a branch in `_import_link`.

## Watched inbox

`fretbook/inbox.py` (`InboxWatcher`) is a thread started in the app's lifespan when `FRETBOOK_INBOX_DIR` is set. It does not queue jobs: each poll stats the files, and one whose size and mtime match the previous poll is copied to the upload spool and run through `import_local_file` (the `import.file` path in `jobs/handlers.py`, so sniffing, importers, duplicate and tag handling are shared). Doing it inline keeps the outcome and the file move in one place with no state to lose on a restart; a crash between storing a song and moving its file leaves the file to be skipped as a duplicate. In `move` mode the result decides `processed/` or `failed/` (plus `.error.txt`). In `library` mode nothing is written to the folder; migration 011 `inbox_files` keeps the hash and song id per file, and a changed file is imported with `replace_song_id` so the same song is updated. With sign-in the owner is the user whose email, email local part, display name or subject equals the subfolder name.

## Background jobs

Imports run on a job thread in the web process, reading the `jobs` table. Slow or GPU-bound work (stem separation, transcription, OCR, recognising tabs in video frames) runs in a separate worker, `python -m fretbook.worker [--kinds a,b]`, that claims only its own kinds from the same table and lands its result as a draft for review in the editor. The design is in [design/youtube-tab-import.md](design/youtube-tab-import.md).

- **Claiming.** `JobRunner._claim` is one `UPDATE jobs ... WHERE id = (SELECT ... LIMIT 1) RETURNING *` inside `BEGIN IMMEDIATE`, so two processes never claim the same row. The database is in WAL mode with a busy timeout, which is what lets both processes share the file. `jobs.worker_id` records who claimed it.
- **Registry.** A feature adds its handler once with `@job_kind("name", worker_only=True)` (`fretbook/jobs/registry.py`; the built-in `echo` kind is in `jobs/worker_kinds.py`). The web process registers only kinds that are not worker-only, so it leaves the rest queued. `FRETBOOK_WORKER_KINDS=a,b` moves other kinds, such as `import.youtube_frames`, to the worker too; start the worker with a matching `--kinds`.
- **Recovery.** A process requeues only the interrupted jobs of the kinds it claims, so restarting the web process never steals a job a worker is running. Restart a crashed worker to requeue its jobs.
- **Presence.** A worker heartbeats every 5 s into the `workers` table (migration 004). `GET /api/meta` returns `worker_kinds`, the kinds with a heartbeat in the last 30 s, so the UI can hide features that no worker serves. Until then a job of that kind simply stays `queued`.
- **Deployment.** The worker needs the same SQLite file and data directory as the web process, so it runs on the same host or on one that mounts the same volume (SQLite over a network filesystem is not supported). `Dockerfile.worker` builds it on an NVIDIA CUDA image and `docker compose --profile worker up` starts it. Start the web process first: it owns schema migrations.

## Automatic sync

`POST /api/songs/{id}/autosync` queues an `audio.autosync` job (`fretbook/jobs/autosync.py`, a normal kind, so it runs in the web process unless `FRETBOOK_WORKER_KINDS` moves it to a worker). Its result is a proposal, `result.autosync`: anchors keyed by played bar index, a 0 to 1 confidence for each, the overall confidence and the bars to check. It saves nothing and needs no migration; the browser applies a proposal through the existing `PATCH /api/songs/{id}/sync`, so revisions and conflicts behave as for tapped marks.

- `fretbook/audio/beats.py` is numpy only (no librosa, madmom or torch, which would triple the image). It decodes (a WAV is read directly, everything else through `ffmpeg`), takes a log-spectral-flux onset envelope (full band for the beat, and a low band under 250 Hz for the bar's first beat), estimates the period by autocorrelation with the score's tempo as a log-Gaussian prior (one octave wide, so a recording a few tens of percent off the written tempo is followed but half-time is not chosen), and tracks beats with Ellis-style dynamic programming. The period can be one value per frame, which is how tempo changes are followed.
- `fretbook/score/autosync.py` maps the beats onto the score's quarter-note timeline for the *played* bars (`played_bars`), so repeats, signatures and tempo changes come from the score. A Viterbi pass over "which beat does bar *k* start on" rewards low-band onsets at bar starts and charges a fixed cost when a bar is a beat early or late of its length, so a beat the tracker dropped moves a few bars rather than every later one. Bar 0 is pulled toward the first attack in the audio. Scores with tempo changes get a second and third tracking pass whose period follows the first alignment. A score whose bars are not whole quarter notes (7/8) is tracked in eighths.
- Confidence for a bar is the strength of the low-band onset at its start against the song's beats, and how steady the beat intervals are around it. Bars under 0.5 are listed in `low_confidence`.
- `fretbook/audio/synth.py` renders a score to rough audio with known bar times, and `scripts/autosync_eval.py` prints the error table (median, 95th percentile and maximum error, in milliseconds, per case). `tests/test_autosync.py` runs a smaller version with thresholds.

On the client, `web/src/lib/autosync.ts` builds the click track (an accent on each bar start, a click on each beat after it, in compound time one a dotted quarter) from the proposal's anchors and the same `measureStarts` the player uses, and `AutoSyncSheet.svelte` runs the job, previews it on its own `Audio` element and `Clicker`, and hands the anchors to `TabPlayer`, which saves them like tapped marks.

## Stem separation

`POST /api/songs/{id}/stems` queues an `audio.stems` job (`fretbook/jobs/stems.py`), a worker-only kind: the web process refuses the request with `stems.noWorker` unless a worker with a recent heartbeat claims the kind, so the UI hides the feature otherwise (`GET /api/songs/{id}/stems` returns `available`). `fretbook/audio/stems.py` runs Demucs (`htdemucs_6s` by default, which also splits guitar and piano; `htdemucs` for four stems), imported lazily because torch is large and lives only in `requirements-stems.txt`. `python -m fretbook.worker` leaves `audio.stems` out of the kinds it claims when `demucs` cannot be imported, so a worker never advertises what it cannot run. Stems are encoded to mp3 with ffmpeg and stored as media of kind `stem-<name>` beside the song's `audio`; nothing in the schema changes. They are left out of library backups (they are large and can be made again), and replacing the song's audio deletes them, since they would no longer line up. A run replaces the stems it makes; `DELETE /api/songs/{id}/stems` removes them all.

On the client, `web/src/lib/stems.ts` has `stemGains` (mute and solo as in the track mixer) and `StemPlayer`. The player's own `<audio>` stays the clock, so sync marks, loops, the metronome and speed changes work as before. The `StemPlayer` silences it and plays one extra `Audio` per stem, copying its play, pause, seek and rate, and moving a stem back when it drifts more than 80 ms. Mixer settings are kept per song in `localStorage` (`StemMixer.svelte`).

## Listening to the microphone

`web/src/lib/listen/` is the pitch-detection engine for tuner, wait mode and scored play. `engine.ts` (`PitchEngine`) is pure DSP with no browser APIs: it takes audio blocks and returns `{time, frequency, clarity, midi, cents, onset, onsetTime}` events. It combines an MPM pitch detector (`mpm.ts`, FFT autocorrelation, a window of about 85 ms at 48 kHz so B0 at 31 Hz fits) and a spectral-flux onset detector (`onset.ts`) that also confirms a steady pitch change for legato. An expected note can be supplied to resolve octave errors. `processor.ts` runs the engine in an `AudioWorklet` (bundled as its own module through `?worker&url`) and `input.ts` is the main-thread side: device list, `getUserMedia` with echo cancellation, noise suppression and auto gain off, channel selection, level meter and the "not HTTPS / not allowed" problems. `calibration.ts` measures round-trip latency and jitter via an interactive click/tap wizard, warning on Bluetooth output or high jitter, with calibrations stored per device pair in `audio_calibrations` per user. `harness/` holds the plucked-string synthesizer, WAV reader and the accuracy test (`accuracy.test.ts`, which prints a report); committed fixtures are in `fixtures/`.

## Tuner

`TunerSheet.svelte` is a sheet opened from the song page (preloaded with the track's `tuning_midi` and capo through `ui.tunerRequest`) or from the top bar (chromatic plus the presets in `web/src/lib/tuner.ts`). It reads pitch events from `startListening`, but recomputes note and cents itself from the event's frequency so the A4 slider (432 to 446 Hz) needs no restart. `lib/tuner.ts` holds the pure logic (nearest string, needle position, `PitchSmoother`: median filter with a dropout hold, a ±1.5 cent dead zone, `TuneTracker`: a string within ±3 cents for 1 s counts as tuned and the sheet shows All strings in tune, the success chime, the sine reference tone). The sheet lays the strings out as a headstock (low strings left, high right) with an Auto toggle that, when off, locks to the tapped string. Nothing leaves the browser.

## Wait mode

`web/src/lib/listen/wait.ts` is the pure part. `buildWaitSteps` walks the chosen track in played order (repeats and jumps expanded, as in `playback.ts`) and returns one step per beat the player has to play: expected pitch is `tuning_midi[string] + capo + fret`, tied notes, rests and grace notes are skipped, dead notes accept any attack, voices on the same beat are merged, and a beat of two or more different pitch classes becomes a `chord` step (with `pcs`) unless the `chords` option is off, in which case a chord accepts any one of its notes. `WaitMatcher` consumes `PitchEvent`s: an attack after the cursor stopped (with 80 ms of grace for latency) arms it, and a reading within 40 cents of the expected note within 300 ms of that attack is a hit, in any octave unless the option says otherwise. Needing a fresh attack keeps a ringing previous note, or the same note twice, from counting twice. Chords are judged on chroma, not on the single pitch the detector makes of them: `chroma.ts` folds an 8192-sample FFT (about 170 ms at 48 kHz, since a 4096 window cannot resolve E2 from F2) into twelve pitch-class energies, only while `PitchEngine.setChroma(true)` is on, and `chromaScore` combines the share of energy on the chord's notes with how many of its notes are present. `WaitMatcher.pushChroma` is armed by a spectral-flux onset (never the legato pitch-change onsets, which fire at random on chords), then scores readings whose whole window came after the strum, up to 1.2 s later, and accepts at 0.6. On synthesized strums that threshold passes the right chord (0.74 to 0.92), a chord with a string missing and one wrong string (0.57 to 0.64, borderline by design), and rejects other chords including the close ones (C for Am and back, at most 0.56). `chordTones.ts` turns a chord name into pitch classes and `chordSheetWait.ts` lists a sheet's chords as steps (transposition and `{capo}` applied), so `ChordWait.svelte` reuses `WaitRun` for chord sheets with the sheet's highlight keyed by block, line and segment. `waitRun.ts` owns the microphone session, tells the engine the expected note, and runs the hint timer.

`TabPlayer.svelte` wires it to alphaTab's synth: on `playedBeatChanged` it looks the beat up by played bar and `displayStart` (ticks match the score document) and, if it is a step, pauses; a hit calls `play()`. A click on the score (`beatMouseDown`) calls `WaitRun.reposition(tick)`, which drops the current wait and stops on the clicked beat if it is a step (alphaTab's own seek-back and seek events are never read as clicks). The chosen track is muted in the synth at runtime (not saved with the mix). Wait mode is for the synth only, never a recording, because stopping a recording at every miss does not work. The synth also loops A to B now, which only audio playback did before. Wait options are saved per song with the practice settings; whether it is on is not, since it needs a click to open the microphone. The end-to-end test plays a rendered WAV through Chromium's fake microphone (`--use-file-for-fake-audio-capture`); the file loops, and wait mode waits, so it passes from any point in the loop.

## Scored play-along

`web/src/lib/listen/scored.ts` is the pure part. `buildScoredSteps` takes the beats of `buildWaitSteps` and gives each the time it is due on the playback clock (`highwayStarts` + `timeAtBarPosition`, the clock the highway uses, so it is the same for a recording with sync marks and for the synth). `Scorer` grades one pass over a range of the song: an attack within 100 ms of the due time with the right pitch (within 40 cents, any octave unless the option says otherwise, any one note of a chord (chords are not checked by pitch content here), any attack for a dead note) is a hit, up to 300 ms away it is early or late, the right timing with another pitch is wrong, and a note with no attack by then is missed. Each attack grades at most one note, and attacks that match nothing are counted as extras. Hit counts 1, early or late 0.5, wrong and missed 0; extras are reported but do not lower the score. Stars are 3 from 90%, 2 from 75% and 1 from 50%.

`scoredRun.ts` owns the microphone session and maps the detector's clock (`ListenSession.currentTime`, the AudioContext clock) onto the song's clock: `song now − (mic now − event time + calibrated latency) × playback rate`, so slowing the song down moves the due times but not the player's latency. It advances the scorer every 100 ms so misses show up live, and ends the pass when the song reaches the end of the range (the end of the loop, or the song), or on request. `TabPlayer.svelte` runs it with the recording or the synth (the chosen track is muted in the synth, as in wait mode); a seek starts a new pass from there, and a loop turnaround ends the pass instead of going round again. Gems on the highway take the colours of their grades, and so do the note heads and fret numbers in the notation (`alphatab/gradeColors.ts` sets each note's style and `TabPlayer.svelte` redraws the score, batched, as grades arrive; the colours clear when scoring stops).

Results (`ScoreResults.svelte`) show overall accuracy, stars, the counts, accuracy per named section, a heatmap of bars and "Practise this section", which sets the loop to the weakest four bars or a chosen section. `lib/scoreLog.ts` keeps the latest 30 results and the personal best for each song, loop and speed in `localStorage` (`fretbook.scores.<song>`). The practice log (`lib/practiceLog.ts`) gets the time as a session with mode `scored` and the latest pass's accuracy as its `score`. Bleed is a heuristic: with a recording, four or more attacks more than a second from any note of the track, and at least half of all attacks, shows a headphones warning; it never changes the score.

## Fretboard

`web/src/components/Fretboard.svelte` only draws: it takes the tuning (4 to 8 strings), capo, fret count, the notes lit now and the faded upcoming ones, a label mode and a handedness flag, so the tuner, wait mode and trainers can reuse it. `web/src/lib/fretboard.ts` holds the pure parts: `buildFretEvents` (beats of a track in played order), `focusAt` (current and next notes at a bar and tick), `positionInBar` (a recording's clock to ticks), fret spacing and the dot labels. Frets count from the capo, so the capo is the nut. The options live in the per-song practice settings (`fretboard`). Giving it an `onselect` handler turns every fret into a tap target, which the note trainer uses.

## Ear and fretboard trainer

`web/src/components/TrainerView.svelte` (route `/tools/trainer`) is a thin shell over the pure modules in `web/src/lib/trainer/`: `fretboardGame.ts` (questions, tap and played-note checks, `StableNote` to debounce pitch readings, per-string statistics), `ear.ts` (interval and chord-quality pools, questions, answer checks, session summary), `chordPlay.ts` (answering the chord game by strumming: `ChordAnswerMatcher` takes the chroma readings of `lib/listen`, arms on an attack, and compares each reading whose window came after it with every root and chord quality of the pool by cosine similarity to the chord's pitch classes after dropping weak bins; the question's chord must fit as well as the best one (equal-note chords such as augmented triads tie), two agreeing readings are a right answer and six naming another chord a wrong one, and the component feeds it only after the question has stopped playing), `session.ts` (timed rounds with an injected clock), `store.ts` (per-string stats and best scores in `localStorage`) and `audio.ts` (Web Audio voices). Microphone answers reuse `startListening` from `lib/listen`. A finished game is posted to `POST /api/practice/exercises` (table `practice_exercises`, migration 013) because it belongs to no song; the practice stats sum its seconds into the same per-day totals as song sessions, so goal, streak and heatmap count it, and list it under `exercises`.

## Chord diagrams

All in the browser (`web/src/lib/chords/`); the server only stores the ChordPro, including any `{define:}` lines. `theory.ts` reads a chord symbol (the same roots and slash basses `transposeChord` accepts) into the pitch classes a voicing must sound. `voicings.ts` generates the shapes: for every window of four frets it tries each string as muted, open or fretted, keeps the fingerings that contain every essential note (the fifth is optional in sevenths and ninths), have the root or slash bass lowest (not required for ukulele, whose shapes are often inversions), only mute strings on the bass side, and need at most four fingers, then ranks them (open strings and low positions first, barres and stretches last) and keeps a few per position. **Source and licence:** the shapes come from this generator and the open-string pitches in `lib/tuner.ts` alone. No third-party chord table or font is used, so there is no data licence to carry, and the result is the same for any tuning. Strings are numbered lowest first, as in ChordPro `{define:}` and as a diagram reads left to right, which is the reverse of the tuner's order (`physicalTuning` converts).

`{define:}` is parsed in `chordpro.ts` (`base-fret` and `frets`, plus the old `{define: Am 1 x 0 2 2 1 0}` form; fingers are ignored) and is offered first for the chord of that exact name and string count. The strip lists the chords as shown after transpose, so a define for `Am` no longer applies once the sheet shows `Bm`. A `{capo:}` is not applied to the shapes (the written chords are the shapes you finger); it raises the pitch of the strum and is noted above the strip. Applying a capo suggestion (`CapoSuggestions.svelte`) is a view setting in `ChordSheetView.svelte` and saves nothing: it replaces the sheet's capo, and the shapes shift by the sheet's capo minus the applied one on top of the transpose, so the strum and chord-wait (`chordSheetSteps` takes the capo as an override) still sound the original pitch. The instrument, tuning and picked voicing per chord are kept in `localStorage` per song (`choice.ts`), the voicing as its frets so a later change to the ranking does not move it. `layout.ts` turns a voicing into marks that `ChordDiagram.svelte` draws as SVG and `export/chordDiagrams.ts` draws into the PDF with `pdf-lib`. `strum.ts` holds the note schedule (pure) and a small WebAudio plucked-string voice. `ChordLibraryView.svelte` (`/tools/chords`) searches a name and lists up to twelve voicings.

## Setlists

A setlist (`setlists` table) is a named, ordered list of entries (`setlist_entries`: song, position, a free-text `note`, and a `transpose` in semitones that applies to chord sheets). An entry has its own id, so a song can be in many setlists and twice in one. Both tables cascade, so deleting a song or a setlist removes its entries; `adopt-local` moves a user's setlists with their songs. `fretbook/storage/setlists.py` holds the queries and `api/setlist_routes.py` the routes. Every query is scoped by owner, a write names only songs the caller owns, and reads join songs on the setlist's owner, so titles never leak across users. Reordering and editing send the whole list (`PUT /api/setlists/{id}/entries`), which is saved in one transaction. The "Add to setlist" sheet (song page and library card) appends one song with `POST /api/setlists/{id}/entries`.

The backup manifest gains a `setlists` array (`id`, `name`, entries as `song_id`, `note`, `transpose`). It is additive, so `format_version` stays 1 and older readers ignore it. Restore keeps a map from archive song ids to the ids the songs ended up with (a skipped song maps to the one already in the library; a copy may get a new id) and drops entries it cannot map, with a warning.

In the web app, `SetlistsView`, `SetlistView` (rename, add songs, drag or Alt+arrow reorder with an `aria-live` announcement, notes, transpose, PDF) and `SetlistPlayView` (previous and next through `/setlists/:id/play/:n`, which renders `SongView` with the entry's transpose) sit behind three routes registered in `App.svelte`; `lib/setlists.ts` is the pure logic. `lib/export/setlistPdf.ts` renders each song with the single-song exporters, appends their pages with `pdf-lib`'s `copyPages`, and puts a contents page in front.

## Offline use

The web app is installable (`web/public/manifest.webmanifest`, icons in `web/public/icons/`) and works offline through a service worker. `vite build` runs the `fretbookServiceWorker` plugin in `web/vite.config.ts`, which bundles `src/sw.ts` into `dist/sw.js` with the list of build files to precache and a version hash of them. Everything is relative to the worker's scope, so a `FRETBOOK_ROOT_PATH` prefix needs no setting. The server already serves `sw.js` and the manifest from the build folder, and `index.html` at every path with the `<base>` rewritten, which is why the worker saves the shell under the scope URL.

The worker's decisions live in `lib/offline/swCore.ts` (with its fetch, caches and scope injected, so Vitest runs them against an in-memory cache):

- build files (`assets/`, fonts, the soundfont) come from the shell cache `fretbook-shell-<version>`; a new build installs into a new cache, takes over at once, and deletes the old one. Install fails, and so retries on the next load, if the shell is not HTML or came through a redirect (a sign-in page).
- navigations are network first with the saved shell as the answer when the network fails or takes over 4 s; `auth/*` and every non-GET request are never touched.
- `GET /api/songs/{id}`, `/api/setlists/{id}` and `/api/songs/{id}/audio` are "saved on purpose": the page puts them in the `fretbook-data` cache (`lib/offline/store.ts`), the worker refreshes a saved document whenever it is fetched online, forgets one the server answers 404 for, and serves saved audio with real `206` range answers (Cache storage ignores `Range`, and Safari insists on it). Documents that were not saved are never kept.
- library lists and `meta`, `me` and `tags` are network first and kept as they pass, so the screens around a saved song start offline. Whatever the worker cannot answer is a `503` with the error key `offline.unavailable`.

`lib/offline/registry.ts` is the list of what was saved (in `localStorage`; a song kept by a setlist and by itself is only deleted when neither wants it). `lib/offline/queue.ts` and `queueState.svelte.ts` hold edits made with no network, also in `localStorage` (about 5 MB per origin, enough for very many songs but not for a big import; a refused write is reported to the editor as a failed save). `updateSong` in `lib/api.ts` queues an edit when the request fails with no network and answers with the song as it would be saved, at the same revision; a second offline save of the same song replaces the first and keeps its base revision. `flushQueue` in `lib/offline/offline.svelte.ts` sends them in order when the browser comes back online and at start. A 409 does not retry: the edit becomes a conflict the user settles in `OfflineStatus` (keep theirs, or re-save on top of the latest revision), which is deliberately simpler than the editor's own sync-mark merge. Small writes use a second queue, `lib/offline/ops.ts` (typed operations, `localStorage` too): `patchSync` (sync marks and BPM), `setSongTags`, `setFavourite` and `recordPracticeSession` queue an op when the request fails with no network. A later sync, tag or favourite change for the same song replaces the earlier one; practice sessions are append-only and all stay. `flushQueue` sends them after the edits, in order; a refusal by the server (for example the song was deleted) keeps the op as failed until the user dismisses it in `OfflineStatus`.

Playwright blocks service workers by default (`serviceWorkers: "block"` in `playwright.config.ts`) because precaching the whole app per test is slow; `e2e/offline.spec.ts` turns them on.

## Practice log

`practice_sessions` holds one row per stretch of playing (song, track, optional loop, `started_at`, the player's local `day`, `duration_seconds`, time-weighted `speed`, `mode` of free, wait or scored, and a `score` for scored sessions); `practice_goals` holds one daily-minutes goal per user. Both cascade from the song or user. `storage/practice.py` holds the queries and the dashboard arithmetic and `api/practice_routes.py` the routes (`POST /api/practice/sessions`, `GET /api/practice/stats?today=`, `GET`/`PUT /api/practice/goal`, `GET /api/songs/{id}/practice`, `GET /api/practice/recommendations?today=`). Every query is scoped by owner and a session may only name a song the caller owns. `day` is chosen by the browser (a day more than two days from the server's is refused), so the heatmap and streaks follow the player's midnight; the server computes them relative to the `today` the browser sends. A streak is a run of consecutive days with any practice and survives until a whole day has passed without one.

The backup manifest gains `practice` (`sessions`, `exercises` for trainer games, and for a single user's archive `goal`), additive like `setlists`; archives without `exercises` still restore. Restore validates sessions and trainer games one by one, remaps song ids through the same map setlists use, skips session and game ids already in the library (another user's id gets a fresh one), and drops the rest with one `backup.practiceDropped` or `backup.exercisesDropped` warning.

In the browser, `lib/practiceLog.ts` turns playing into sessions (`PracticeTimer`, with an injectable clock) and holds the ring, heatmap and day arithmetic. `TabPlayer` feeds it from its playing state (in wait mode, waiting for a note also counts), flushes on pause timeout, leaving the player, and `pagehide` (a `keepalive` request). `PracticeView` is the dashboard at `/practice`; `SongPractice` is the history under a tab.

## Lessons and courses

Lessons are files, not rows, so they can be written by hand, reviewed in a pull request and shared as zips. `fretbook/lessons/format.py` is a pure parser (a strict subset of YAML front matter, Markdown body, and fenced `fretbook:<kind>` blocks with validated parameters) that reports problems with line numbers; the editor preview calls the same parser through `POST /api/lessons/preview`, so there is one grammar. `catalog.py` reads the built-in folder (`fretbook/lessons/builtin/`) and `FRETBOOK_LESSONS_DIR`, per request, with the user's file winning per lesson; one bad file is collected as a problem and never stops the rest. Every id becomes a path, so ids are matched against a tight pattern before any file is touched. Writes go only to the user folder, through a temp file and rename, and a zip pack is validated whole (reusing `importers/zip_safety.py`) before anything is written.

`unlock.py` computes, from the catalogue and one user's progress, which lessons are locked, available or completed and where "continue" goes. Prerequisites default to the previous lesson; cycles and unknown ids are dropped with a problem. Progress is migration 015 `lesson_progress`, keyed by owner, course id and lesson id with no foreign key to lessons (they are files), and is included in a single user's backup. A pass condition is evaluated on the server by `format.passes`: a result the player reports (the song page opened with `?lesson=<course>/<lesson>` posts a whole-song scored run or a played-through wait run to `POST /api/courses/{course}/lessons/{lesson}/progress`; `web/src/lib/lessonRun.ts` decides what counts), or, when the condition names a library song, the best matching run read from `practice_sessions` (tempo is the song's `bpm` times the logged speed; wait mode counts only sessions with `completed = 1`, migration 016, which the player sets when `WaitRun.completed` is true). Completion is never taken back. Without sign-in the one user may edit lessons; with sign-in only administrators may.

## Note highway

`web/src/components/Highway.svelte` renders a 60 fps 2D Canvas scrolling note highway driven by the same playback clock as the score cursor (both audio with sync marks and synth with repeats and tempo changes). `web/src/lib/highway.ts` holds the pure timeline compiler (`buildHighwayTimeline`), chord identifier (`identifyChord`), binary-searched viewport windowing (`visibleWindow`), wait-mode / scored-play gem state resolver (`resolveGemState`), and canvas renderer (`drawHighway`). Gems carry fret numbers, sustain tails (extended across ties), technique glyphs and connectors, chord blocks with chord names, bar/beat lines, and section flags. The song page switches between `tab`, `highway` and `split` views (`ui.playerView`, remembered per user in `localStorage`).

### Difficulty and recommendations

`score/difficulty.py` rates each track 1 to 10 from six measured factors (density at tempo, position shifts, stretch, techniques, chord changes, rhythm) and returns each factor with its raw measurement, so the UI words the explanation. `songs.difficulty` (the preferred track's level, for sorting and filtering without reading scores), `difficulty_detail` (every track's breakdown as JSON) and `difficulty_version` are set wherever a score is written (`create_song`, `update_song`, `update_sync`). `SongRepository.refresh_difficulty` runs at start-up and rates rows with no version or an older one, so bump `difficulty.VERSION` when the numbers change. A chord sheet is rated by `estimate_chordpro` from four factors (different chords, barre chords, extended chords, changes per line), with the barre classification done on the sheet's six-string `{define:}` fingering or else the best voicing of `fretbook/chords/voicings.py` (a Python port of `theory.ts` and `voicings.ts` for a guitar in standard tuning; keep the two in step) and the extended classification done from the chord name; a sheet with no chords has `NULL`. `recommend.py` holds the pure rules for the practice page's suggestions (stretch songs, weak loops, spaced review); `PracticeRepository.recommendations` gathers the rows.

The admin dashboard (`GET /api/admin/storage|jobs|workers|system`, `POST /api/admin/storage/cleanup` and `/api/admin/jobs/{id}/cancel|retry`) lives in `api/admin_routes.py`, with the queries in `admin_stats.py` and owner-less job methods on `JobRunner`. Orphaned media are files under the media folder that no `media.storage_relpath` names; the sweep skips files younger than an hour (`save_file` moves a file in before it inserts the row), symlinks, and anything outside the media folder. Only `queued` jobs are cancelled (one `UPDATE ... WHERE status = 'queued'`, so it cannot race a claim); the job becomes `error` with `job.cancelled` and keeps its upload, so it can be retried. `FRETBOOK_USER_QUOTA_MB` is enforced in `MediaStore.save_file`, which every write path uses; it raises `QuotaExceeded`, which a route answers with 413 `storage.quotaExceeded` and a job records as its `error_key`.
